## Problem Statement

Meeting notes for customer requirements are a manual, multi-tool, unreliable pipeline: OBS (flaky capture, often loses the other speaker's voice) → Superwhisper (meeting mode broken, input source switching is a mess) → custom prompt → markdown → Google Docs. 1-3 hours lost per week. Meetings are in Polish, which rules out most existing transcription tools. The user is an SSE who needs accurate, traceable requirements from conversations — getting requirements wrong means building the wrong thing.

## Demand Evidence

- Self-funded pain: the builder loses 1-3 hours/week on the manual workflow
- Tried and failed: OBS only captures their own voice (not the other person), Superwhisper's meeting mode "makes a mess with input sources"
- "I need this to correctly capture people's needs, to trace back what they said and where the requirements are" — direct user quote
- Laptop is an M5 Max with 128GB RAM — local processing is viable and preferred

## Status Quo

Current hack: OBS → Superwhisper → custom prompt → markdown → Google Docs. Four manual steps. OBS is the primary failure point — captures only local voice, not the other side of the conversation. After recording, they must find the output file on disk and push it to Superwhisper manually. Superwhisper's built-in meeting mode was tried and fails on input source switching.

## Target User & Narrowest Wedge

**Target user:** Jonatan, SSE. Needs to capture customer requirements accurately, trace back to what was said in meetings, and identify where requirements are embedded in the conversation flow.

**Wedge (revised):** Reliable system audio capture triggered by ambient audio detection (Chrome/Zoom outputting meeting audio), with calendar as a metadata hint, not the primary trigger. A clean WAV file in a predictable location, consumable by Superwhisper or the built-in pipeline.

**Full vision (user's choice):** Capture + local Polish Whisper.cpp transcription + speaker diarization + markdown output + Google Docs auto-upload. Replaces the entire chain.

## Constraints

- macOS-only (primary platform, M5 Max 128GB)
- Polish language meetings (rules out English-only transcription services)
- Local processing preferred (privacy, no per-minute API costs, M-series neural engine)
- Must handle Google Meet, Zoom, Microsoft Teams
- Capture must be zero-effort — no manual start/stop, no input source management

## Premises

1. **Capture is the bottleneck, not transcription.** OBS losing the other side of the conversation is the first thing to fix. Transcription quality doesn't matter if the audio is broken. (AGREED)

2. **Ambient audio detection is the primary trigger** — not calendar. Detect when Chrome/Zoom is actually outputting meeting audio. Calendar is a metadata hint (event name, attendees), not a reliable start/stop signal. Rescheduled meetings, Slack huddles, and pasted links would be missed by calendar-only. (REVISED from "calendar is the right trigger" after cross-model challenge)

3. **Polish language is the moat.** Most meeting recorders are English-first. Local Polish transcription on Apple Silicon is the differentiator — and rules out most off-the-shelf tools.

4. **Local-first processing on M5 Max.** 128GB RAM and M-series neural engine make local inference viable. No cloud dependency, no per-minute API costs, no data leaving the machine.

5. **Full pipeline is the target, but capture-first is the path.** Even though the user chose the full pipeline approach, the 48-hour prototype should prove capture reliability before integrating transcription. Superwhisper can consume the output in the meantime.

## Approaches Considered

### Approach A: "Just Record" — Minimal Viable
Menu bar app, ambient-audio-triggered capture, WAV output. Calendar integration for metadata only (event name, attendees). No transcription. Ships in days.

### Approach B: "Full Pipeline" — Ideal Architecture (CHOSEN)
Capture + local Polish Whisper.cpp transcription + speaker diarization + markdown output + Google Docs auto-upload. Replaces entire chain. MENU bar app with history, settings, manual override.

### Approach C: "Audio Dashcam" — Creative
Always-on ring buffer (last 45 min). Keyboard shortcut to save. Never miss an ad-hoc call. Privacy UX is the hard part.

## Recommended Approach

**Approach B (Full Pipeline) with a phased build:**

**Phase 0 — Capture Proof (this week):** Command-line Swift binary. Not a menu bar app, not a calendar integration — a single-purpose binary that opens an aggregate audio device, records for a duration specified via `--duration`, and saves a stereo WAV (mic on left channel, system output on right channel). This channel separation gives diarization a strong signal later: local speaker is always channel 1, remote is channel 2. Prove that system audio capture works with both speakers in a Google Meet. Threshold test: 30-second recording with both voices audible. If this fails, nothing else matters.

**Phase 1 — Auto-Capture (week 1-2):** Swift menu bar app. Ambient audio detection: monitor default system output device. Start recording when volume exceeds -40dBFS for 2+ consecutive seconds. Stop when volume remains below -60dBFS for 30+ consecutive seconds. Save 16kHz 16-bit WAV to `~/MeetingRecordings/YYYY-MM-DD_HHmmss.wav`. Calendar metadata enrichment via EventKit (event name, attendees) for file naming. Menu bar icon: idle/recording. Global keyboard shortcut (Cmd+Shift+R) for manual toggle. Superwhisper compatibility: output file format matches Superwhisper's expected input directly, and output lands in `~/MeetingRecordings/` — no manual file hunting.

**Phase 2 — Transcription (week 3-4):** Integrate Whisper.cpp. Start with base large-v3 model (built-in Polish support). If accuracy <90% on test meetings, explore Polish business conversation fine-tuning. Post-meeting pipeline: raw text → markdown with word-level timestamps. Run on M-series Neural Engine. Output to `~/MeetingRecordings/YYYY-MM-DD_HHmmss.md` alongside the WAV. Superwhisper becomes optional fallback — built-in pipeline is now the default.

**Phase 3 — Pipeline (week 5-6):** Post-processing prompts. Example: "Extract from this Polish meeting transcript: (1) explicit requirements stated by the customer, (2) action items with who committed to what, (3) decisions made. Output as structured markdown." Speaker diarization: run pyannote (or alternatives) against 5 recorded Polish meetings. If word-level accuracy <70%, explore alternatives or ship unlabeled transcripts. WAV auto-deletion after successful transcription (configurable). History browser in menu bar app.

**Phase 4 — Google Docs & Polish (week 7+):** Google Docs API upload via OAuth with macOS Keychain credential storage. Markdown → formatted Google Doc. Recording search, settings panel, preferences.

## Success Criteria

**Phase 0 (Capture Proof):** 30-second Polish Google Meet recording with both speakers clearly audible in a single WAV file, no manual input source management.

**Phase 1 (Auto-Capture):** 30-minute Polish Google Meet, auto-triggered, both speakers audible, zero manual setup. False positive rate <1/day (should not record music or background noise more than once per day).

**Phase 2 (Transcription):** Polish business conversation accuracy >90% on a held-out test set of 5 meetings.

**Phase 3 (Pipeline):** 60-minute meeting → completed markdown output in <10 minutes (transcription only). With diarization: <15 minutes. Post-processing extracts requirements with >80% recall (finds >80% of requirements a human would identify).

**Phase 4 (Docs Upload):** Meeting ends → formatted Google Doc within 15 minutes. No manual steps.

## Technical Risks

1. **macOS system audio capture.** Modern macOS (especially M-series) does not expose system audio capture via a straightforward API. ScreenCaptureKit requires screen recording permission and may not capture arbitrary app audio independently. CoreAudio aggregate devices require driver-level setup (BlackHole, Loopback). **Mitigation:** Phase 0 tests both approaches on a real Meet call before committing.

2. **Ambient audio detection false positives.** Monitoring default system output for volume threshold will also fire for music, notifications, video playback. Distinguishing "meeting audio" from "anything making sound" is non-trivial. **Mitigation:** Accept false positives in Phase 1. Refine with VAD or app-specific detection in Phase 2+. Target <1 false trigger per day.

3. **Polish diarization accuracy.** pyannote-audio is primarily trained on English. Polish conversational diarization (especially with English business term code-switching) is not proven. **Mitigation:** Evaluate against real Polish meetings in Phase 3. If <70% accuracy, skip diarization and output unlabeled transcripts.

4. **Whisper.cpp latency on long meetings.** Local processing is fast (~realtime for large-v3 on Neural Engine), but a 60-minute meeting could take 5-10 minutes for transcription alone. Adding diarization doubles this. **Mitigation:** Phase 2 targets transcription-only <10 minutes. Diarization is additive and optional.

## Failure Modes

| Scenario | Response |
|---|---|
| Audio capture fails to start (permission denied, device unavailable) | Menu bar icon shows error state. Notification: "Recording failed — check microphone permission." |
| Ambient detection misses a meeting (audio too quiet, threshold too high) | Manual toggle available via Cmd+Shift+R. User can start recording anytime. |
| Whisper.cpp crashes mid-transcription | WAV file preserved. Retry on next app launch. Mark recording as "transcription pending." |
| File already exists at target path | Append suffix (-2, -3). Never overwrite. |
| OAuth token expires during Google Docs upload | Token stored in macOS Keychain with refresh lifecycle. On expiry, prompt user to re-auth. Upload retries once. |
| Disk full during recording | Monitor available space. Warn if <500MB remaining. Stop recording gracefully — partial file saved. |
| App killed mid-recording | SIGTERM handler flushes audio buffer and closes WAV file before exit. Recording is recoverable. |

## Permissions

macOS entitlements required on first launch:
- **Microphone** — for capturing local voice via aggregate device
- **Screen Recording** — required by ScreenCaptureKit for system audio capture (even without video)
- **Calendar (EventKit)** — calendar metadata enrichment (optional, Phase 1+)
- **Accessibility** — global keyboard shortcut registration (Cmd+Shift+R)

First-run flow: present a single onboarding window listing each permission, why it's needed, and a "Grant" button that triggers the system prompt. If any permission is denied, the feature degrades gracefully (e.g., no calendar metadata, no system audio = app doesn't work — warn explicitly).

## Data Retention & Privacy

- Raw WAV files: auto-delete after successful transcription (configurable — user can set retention to "never delete," "24 hours," "7 days," or "after transcription")
- Transcripts (markdown): kept indefinitely in `~/MeetingRecordings/`. User-owned, user-deletable.
- No audio or text leaves the machine. All processing (capture, transcription, diarization) is local.
- Google Docs upload is the only network egress — user must explicitly authorize OAuth. Without it, transcripts stay local.
- No telemetry, no analytics, no phoning home.

## Verification

- **Phase 0:** Manual test — record a real 30-second Polish Meet call with both speakers. Verify both voices in the WAV.
- **Phase 1:** Run for 1 week as daily driver. Track: recordings started/stopped correctly, false positive count, missed meetings.
- **Phase 2:** Test Whisper.cpp against 5 Polish meeting recordings. Measure WER (word error rate) against human transcription. Target <10% WER.
- **Phase 3:** Test requirements extraction against human baseline (how many requirements did the prompt miss?). Test diarization accuracy against hand-labeled speaker segments.
- **Phase 4:** End-to-end smoke test: calendar event → Meet call → transcription → Docs upload. Measure total wall clock time.

Not a menu bar app, not a calendar integration — just a hardcoded script that starts capturing, records for 30 seconds while you're in a test Meet, and saves a clean WAV with both voices. If this doesn't work, nothing else matters. Once it does, you know the capture layer is solvable and you can build the rest.

## Architecture Findings — Auto-Decided

### Finding A1: Two-process architecture (Critical)
**Decision: AUTO-ACCEPT (P5 explicit).** Adopt two-process model: daemon (`com.meetingrecorder.captured`) handles capture + VAD + transcription queue. App (`MeetingRecorder.app`) handles UI. Communication via XPC. Transcription runs in subprocess (`whisper-cli`) without blocking UI.

### Finding A2: Persistence layer (High)
**Decision: AUTO-ACCEPT (P1 completeness).** Add SQLite/Core Data in Phase 1. Single table: `Recording(id, path, status, eventName, attendees, startedAt, duration, retryCount, failureReason)`. Status transitions are atomic DB transactions. File existence is derived, not source of truth.

### Finding A3: Recording state machine (High)
**Decision: AUTO-ACCEPT (P5 explicit).** Define formal state machine: Idle → Detecting → Recording → SilentPause → Saving → Transcribing → Complete → Failed. Each state has entry/exit actions. Invalid transitions assert in debug builds.

### Finding A4: Whisper.cpp integration (High)
**Decision: AUTO-ACCEPT (P5 explicit).** Subprocess approach: `whisper-cli` invoked via `Process`. Model stored at `~/Library/Application Support/com.meetingrecorder/Models/`. Crash isolation: Whisper crash doesn't take down daemon. Model download with progress UI.

## Edge Case Findings — Auto-Decided

### Finding E1: Sleep/wake handling (Critical)
**Decision: AUTO-ACCEPT (P1 completeness).** Register `NSWorkspace.willSleepNotification` / `didWakeNotification`. On sleep: flush WAV, close file, release audio device. On wake: re-initialize audio, return to Idle.

### Finding E2: Audio hotplug (High)
**Decision: AUTO-ACCEPT (P1 completeness).** Monitor `kAudioDevicePropertyDeviceListChanged`. If recording device disappears: save buffer, notify user, attempt re-acquire.

### Finding E3: Partial permissions (High)
**Decision: AUTO-ACCEPT (P1 completeness).** Add 3-second validation pass after recording start: check both channels for RMS > noise floor. If one silent, warn: "Only one side of conversation captured. Check permissions."

### Finding E4: Concurrent recordings (High)
**Decision: AUTO-ACCEPT (P1 completeness).** Transcription queue with QoS: capture = real-time priority, transcription = .background. Test: back-to-back meetings with no audio dropouts.

### Finding E5: File system location (Medium)
**Decision: AUTO-ACCEPT (P5 explicit).** Use `~/Library/Application Support/com.meetingrecorder/Recordings/` — standard macOS location, outside iCloud sync scope. Add startup check for writability.

## Security Findings — Auto-Decided

### Finding S1: Hardened Runtime (Critical)
**Decision: AUTO-ACCEPT (P1 completeness).** Document entitlements strategy: Hardened Runtime, no App Sandbox (incompatible with global keyboard shortcuts), Developer ID signing for distribution. Test notarization flow in Phase 1.

### Finding S2: WAV encryption (Medium)
**Decision: NOTE — document FileVault dependency.** Per-recording encryption optional. For personal tool, FileVault + device passcode is sufficient. Document the gap.

### Finding S3: Superwhisper supply chain (Medium)
**Decision: AUTO-ACCEPT (P5 explicit).** Add privacy note: "Superwhisper fallback may send audio to cloud services. Built-in pipeline guarantees zero network egress."

### Finding S4: EventKit input sanitization (Low)

## Hidden Complexity Findings — Auto-Decided

### Finding H1: Three capture approaches (Critical)
**Decision: AUTO-ACCEPT (P1 completeness).** Phase 0 must test 3 approaches: (1) ScreenCaptureKit system audio, (2) BlackHole + CoreAudio aggregate device, (3) AudioUnit tap on default output. Document results with code. Deliverable: "Swift code that captures stereo system audio."

### Finding H2: Stereo channel complexity (High)
**Decision: AUTO-ACCEPT (P5 explicit).** Rename to "heuristic speaker attribution." Approach: transcribe stereo mix as mono, use channel separation as timeline cue for speaker labels. Accept approximate attribution for overlapping speech.

### Finding H3: VAD threshold tuning (High)
**Decision: AUTO-ACCEPT (P3 pragmatic).** All four parameters configurable from Phase 1. Defaults: -35dBFS start, 1.5s start window, -55dBFS stop, 45s stop window. Log audio level history for post-hoc tuning.

### Finding H4: Launch at login (Medium)
**Decision: AUTO-ACCEPT (P1 completeness).** Add `SMAppService` registration in Phase 1. Calendar metadata requires the app to be running when events change.

### Finding H5: Model download management (Medium)
**Decision: AUTO-ACCEPT (P1 completeness).** 3GB large-v3 model download needs: resume support, checksum verification, progress UI, smaller model option (small.en ~500MB).
